# 架构与扩展边界

## 当前结构

```text
d4box（主仓库）
├── vendor/D4keyHelp（固定提交的上游 submodule）
├── extensions/ahk（自有 Windows 扩展）
├── scripts（启动与 Mac 可运行的项目检查）
└── docs（设计与验证记录）
```

Windows 启动器分别启动上游脚本和扩展脚本，两者独立运行。扩展只读取前台游戏窗口的客户区信息，不调用上游内部函数，不改写上游设置，不接管键鼠。

选择独立进程是为了避免在尚无稳定插件接口时，依赖上游的全局变量、初始化顺序、相对路径和热键作用域。上游 UI 和扩展 UI 目前不合并。

## 后续实施顺序（尚未实现）

1. 在 Windows 验证游戏窗口检测、客户区坐标、DPI 和多显示器行为。
2. 引入截图适配器，保存可在 Mac 离线分析的截图及分辨率、UI 缩放等元数据。
3. 增加局部图像定位与 OCR；识别结果返回边界框和置信度，保持与输入控制分离。
4. 实现滚动搜索状态机：识别、滚动、等待稳定、重复检测、到底判定、超时和取消。
5. 加入操作前置检查和结果确认，再接入实际键鼠执行。

拟议流程：截图 → 识别 → 决策 → 单步输入 → 新截图确认。视觉和流程模块可以在 Mac 使用录制样本测试；Windows 截图和输入必须在目标机器验证。

## 上游协作

- 添加独立能力：在主仓库实现，通常无需修改上游。
- 复用上游界面或内部函数：需要明确接口及版本约束，目前没有接入。
- 接管上游的魔盒流程：需要适配层、上游支持或单独维护的补丁，不能只靠 submodule。
- 同时运行自动输入：先设计输入互斥或暂停协议，目前没有 IPC；不要让两个程序同时控制输入。

如果日后必须修改上游，应明确选择向上游贡献接口或维护 fork，并把补丁及验证范围记录清楚；不要在 submodule 中悄悄留下未提交修改。
